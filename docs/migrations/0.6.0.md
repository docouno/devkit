# Devkit 0.6.0

## Prepare checkouts for each Linux architecture

A single accepted release supports Linux x86-64 and ARM64. From a `0.5.x` checkout on x86-64, preview with `make update to=0.6.0 preview=1`, apply with `make update to=0.6.0`, and review the managed changes in Git. On ARM64, start the update with the native `0.6.0` installer or `npx @docouno/devkit@0.6.0 update . --to 0.6.0`.

Run `make setup` after updating and on each new host. Keep installed dependencies, local readiness records and build outputs out of Git. Include the runner architecture in CI cache keys for native tools and Docker images.

Electron projects own their packaging scripts. The old template archives `release/linux-unpacked`, which electron-builder uses on x86-64. On ARM64, archive `release/linux-arm64-unpacked` instead. For a script that works on both, copy the `package` script from the new Electron template or select the unpacked directory using `node -p process.arch` inside the build container. Packaged Electron applications target Linux.

## Profile-scoped desktop runtime

Preview the upgrade on a branch. The transaction removes the unused `.devkit/runtime/compose.tools.yaml` and `.devkit/compose.workspace.json` from every checkout. In a checkout without a registered Electron component, it also removes the managed desktop Dockerfile, seccomp profile and its two attribution files, and drops the desktop recipe pin. Review these changes alongside `.devkit/manifest.json` and `.devkit/runtime.sha256`. Run `make setup` and `make check` after applying the upgrade.

Use `make doctor`, the checked-in loader (`sh .devkit/runtime/devkit.sh cli doctor . --json`), or CLI `0.6.0+` with any upgraded checkout. External `doctor` through `0.5.1` rejects the new checkout format. On headless checkouts, commands that dispatch to the accepted engine can also report `Missing toolchain pin` from CLI `0.5.1`, and its local `info` fallback reports readiness as `unknown`. See [cross-release dispatch](../upgrades.md#choosing-a-cli-for-headless-projects) for the affected commands.

Adding or registering the first Electron app installs the desktop assets from the accepted release in the registration transaction. A registered app keeps its project-owned Compose definition.

Electron apps registered with an older release keep their accepted development integration on upgrade. New registrations use `development.kind = desktop` for stand reservation and status.

## Adopt the root Cargo workspace

Version 0.6.0 accepts direct updates from 0.5.x. For older checkouts, apply each intermediate release on a branch and run setup and checks before the next update.

- For a schema 1 checkout, use the [0.2.1 bootstrap procedure](../upgrades.md#supported-upgrade-window) first.
- On `0.2.x` or `0.3.x`, start with `npx @docouno/devkit@0.4.1 update . --to 0.4.1`, then follow the `0.4.x` step.
- On `0.4.x`, run `npx @docouno/devkit@0.5.1 update . --to 0.5.1`.

From `0.5.x`, preview the update with the accepted component manifests and locks present.

```sh
make update to=0.6.0 preview=1
```

For Rust projects the preview lists one virtual root `Cargo.toml`, one `Cargo.lock`, a release-managed `rust-toolchain.toml`, and a project-owned `rustfmt.toml`. The transaction transfers compatible component workspace settings, retains the selected dependency graph, and removes the old component locks, pins and formatter configurations. Existing crate names and source directories stay valid. Nested crates in a component workspace become explicit root members.

Preview and apply each validate the merged lock in staging. For graphs that Devkit can verify from the release templates or simple local path dependencies, this step runs before setup without Docker or a populated Cargo cache. For other graphs, such as external crates with custom feature selections, the target release's pinned Cargo must accept the staged lock before the update can proceed. A validation failure leaves the checkout intact.

Cargo validation requires Docker and may fetch the pinned image or missing dependency data. To preview offline, cache the target release, pull the digest-pinned base image from its `runtime/rust.Dockerfile`, and populate the Cargo cache under `DEVKIT_CACHE_DIR`. Then run `devkit --offline update . --to 0.6.0 --preview` with the installed CLI. Use the same command without `--preview` to apply offline.

Resolve conflicts in the 0.5.x project and repeat the preview.

- Two apps created from the 0.5.x Rust API template both declare `name = "devkit-api"`. For example, in `apps/worker/Cargo.toml` change the package name to `"worker-api"`. In that app and its dependents, change Rust references from `devkit_api` to `worker_api`, update Cargo dependency declarations if applicable, and review executable names in scripts or Compose commands. Refresh the old component lock with pinned Cargo, then run the component checks.

  ```sh
  make exec app=worker write=1 network=bridge command='cargo update --workspace'
  make check
  make update to=0.6.0 preview=1
  ```

- If two locks select different compatible versions of a crate from the same registry or Git source, align them on 0.5.x. Inspect the paths and versions in the error, choose the intended version, and run e.g. `make exec app=worker write=1 network=bridge command='cargo update -p serde --precise 1.0.229'`. Check the resulting lock diff and rerun the gates. The migration also checks checksums and dependency edges for each shared package identity.
- Local crates in different directories can keep distinct versions. If two components selected different directories for the same crate name and version, choose a common source or give the crates distinct identities on 0.5.x, then refresh the affected locks before retrying.
- Align differing formatter settings, resolvers, build profiles and inherited workspace lint policies. If two workspaces inherit different README files, set each crate's `package.readme` to its own relative path and remove the conflicting workspace defaults before updating. Review component-wide patches and replacements that would change another component's dependency selection. Move component-local Cargo configuration to the root `.cargo/config.toml` and rebase its relative paths before updating. Resolve any pre-existing destination files explicitly.

Apply the accepted preview, verify the gates, and commit the product and managed changes together.

```sh
make update to=0.6.0
make setup
make check
make test
make build
```

Use the root `Cargo.lock` in CI cache keys. Rust builds and development services share the checkout's `target/`. Existing component `target/` directories can be removed when their artifacts are no longer needed. Review custom scripts or Compose overrides that reference a component-local executable path.

## Recover an interrupted update

If the update stops after writing its journal, run `make recover` before modifying transaction files. If the old loader is still installed (or if a previous recovery was interrupted immediately after rolling `.devkit/runtime/devkit.sh` back to `0.5.x`), run the verified target engine that Devkit cached before starting the transaction. Set `target` and `engine_sha` from the cached target release's `release.json` under `releases/0.6.0/<release-identity>/` (`x86_64-unknown-linux-musl` uses `files.devkit.sha256`; `aarch64-unknown-linux-musl` uses `files["devkit-aarch64-unknown-linux-musl"].sha256`).

```sh
cache=${DEVKIT_CACHE_DIR:-${XDG_CACHE_HOME:-"$HOME/.cache"}/docouno/devkit}
"$cache/engines/$target/0.6.0/$engine_sha/devkit" recover .
```

Recovery verifies the current files and restores the saved bytes from the local journal. It runs offline without Docker. A second recovery succeeds with no pending update. If a file was edited after the interruption, restore its recorded before or after contents and mode before retrying recovery.
