# Devkit 0.5.0 Migration

## Migrate Node workspaces to pnpm

Update on a Git branch without requiring a global CLI install: on `0.4.1`, run `sh .devkit/runtime/devkit.sh cli update . --to 0.5.0 --preview` and then re-run without `--preview`; on `0.4.0`, run `npx @docouno/devkit@0.5.0 update . --to 0.5.0 --preview` (then without `--preview`) or pass `update . --to 0.5.0 --preview` to the [versioned installer](https://github.com/docouno/devkit/releases/download/v0.5.0/install.sh). The transaction creates `pnpm-workspace.yaml` and `pnpm-lock.yaml`, removes the root npm lock and `package.json` workspace list, migrates registered component links to `workspace:*` (`workspace:^` between explicitly public libraries), and removes legacy npm linking keys from `.npmrc`. It retains root dependency declarations, registry routes, token placeholders, product code, product dependency selections, and user scripts. Peer-only local links gain a workspace development dependency while retaining their peer range. When npm installed the same artifact with different transitive versions, migration preserves the variant reached by product dependencies over tooling-only variants. Conflicting product variants require `--reconcile-lock`, which permits explicit transitive resolution changes when the old graph cannot be retained. If an update is interrupted while the old loader is still installed, run `npx @docouno/devkit@0.5.0 recover .` or pass `recover .` to the versioned `0.5.0` installer.

Implicit `.pnpmfile.cjs`, `.pnpmfile.mjs`, and `.pnpmfile.js` hooks are unsupported. Move installation work into package lifecycle scripts, which Devkit runs in its separate offline phase.

If an npm project already contains `pnpm-lock.yaml` or `pnpm-workspace.yaml`, move those files aside before updating. Migration refuses destination collisions before staging changes. Read-only inspection of accepted `0.4.x` projects keeps their npm format and configuration policy. Existing `packageManager` and `devEngines` metadata is preserved; commands run by Devkit use its verified pnpm and container Node pins with automatic manager and SDK installation disabled.

The admitted workspace settings include `minimumReleaseAgeExclude` entries for exact `name@version` selections emitted by pnpm. Wildcards and version ranges in that list are unsupported; sync preserves admitted entries.

The pnpm configuration policy reserves environment names beginning with `PNPM_` or `XDG_`. If a legacy `.npmrc` uses such an authentication placeholder, rename it and its environment variable before updating, for example `PNPM_REGISTRY_TOKEN` to `REGISTRY_TOKEN`. Accepted `0.4.x` inspection keeps the original npm policy; numeric `fetch-retries` and `fetch-timeout` settings are admitted only in pnpm projects.

Each pnpm YAML input is limited to 32 MiB, including standalone locks during registration and saved copies during update or recovery. Local directory and tarball paths retain the native path syntax, including spaces; registration rebases them relative to the new component without permitting checkout escape. Directory snapshots of registered components obey the same application and library dependency rules as workspace links.

Review product-owned scripts and CI commands before running the gates:

- Replace `npm run --workspace=apps/web check` with `pnpm --dir apps/web run check`. Existing `npm run ...` calls inside component `package.json` `scripts` continue to work, and can optionally be changed to `pnpm run ...` to avoid spawning extra `npm` subprocesses.
- Replace dependency mutations such as `npm install zod` with `make exec app=web write=1 network=bridge command='pnpm add zod --lockfile-only --ignore-scripts'` (pass `-w` when running `pnpm add` or `pnpm remove` in the root Node workspace without `app=` or `package=`) and run `make setup`.
- Use `workspace:^` only for runtime links between registered libraries with explicit `"private": false`; publishable packages cannot depend on private libraries or applications. `pnpm pack` rewrites the specifier to a registry SemVer range and Devkit validates the source manifest first.
- Keep npm for optional `npx` CLI entry points and publishing verified `.tgz` archives with provenance.

Run `make setup`, `make check`, `make test`, and `make build`, then review and commit all migration changes. Setup fetches the verified pnpm executable on first use; metadata commands and Rust-only projects do not. For an offline Node checkout, warm the executable and package store with setup while network access is available.

`DEVKIT_CACHE_DIR` defaults to `~/.cache/docouno/devkit` and now includes `tools/`, `pnpm-store/`, `pnpm-cache/`, `cargo/`, and `electron/`. Place it on the checkout filesystem for hardlinks. GitHub Actions can use `${{ runner.temp }}/devkit-cache`; GitLab CI can use `$CI_PROJECT_DIR/.devkit/cache/ci`. Cache keys should include `pnpm-lock.yaml`, `.devkit/manifest.json`, and Cargo locks. If the selected cache is on another mount, the package store falls back to the repository's common Git directory or the non-Git checkout's `.devkit/cache/pnpm-store`; other caches retain their configured locations.

Daily gates and development services protect `node_modules/.pnpm` from writes. Setup and explicit Node write sessions share a mount with the package store while hiding unrelated sibling directories and `.env` credentials. Local registry routes stay in `.npmrc`; networked Node commands receive a sanitized temporary user config, required environment placeholders, and an optional `DEVKIT_CA_CERT`. Offline Node and Rust tasks never receive registry credentials.

Cold pnpm acquisition supports scoped `_authToken=${TOKEN}` (Bearer) and `_auth=${BASIC_AUTH}` (base64 Basic) placeholders. Credentials follow the longest matching registry path and stay bound to the original origin during redirects.

## Sticky ports, preview and connected stands

Automatic managed host ports now use per-checkout leases from `10000-19999` (`DEVKIT_PORT_RANGE=A-B`). Ordinary `make down` preserves addresses; `make down cleanup=1` releases leases after ownership verification while preserving volumes. Existing fixed ports remain fixed. Unknown legacy containers require explicit operator cleanup; Devkit does not adopt them automatically.

Keep pre-upgrade teardown and post-upgrade stand epoch initialization distinct:

- Before upgrading or merging `0.5.0` into a checkout that has a running `0.4.x` stand, run `make down` on the original Docker context so legacy containers stop cleanly. Devkit preserves verified legacy data volumes under their original names; declare Compose `external` volumes for data with a separate lifecycle.
- If an upgraded `0.4.x -> 0.5.0` checkout already contains a `.devkit/state/` directory (which lacks `0.5.0`'s `stand-protocol/receipt.json`), run `make down` once on `0.5.0` before calling early `stand reserve` in that checkout (`make up` and `make dev` record an empty stopped-stand epoch automatically, whereas cold `stand reserve` requires a verified receipt).

Set `DEVKIT_PREVIEW_URL_TEMPLATE` (in the process environment or once in the main checkout's root `.env`, where linked Git worktrees inherit it automatically and any `<worktree>/.env` can override it or disable inheritance with `DEVKIT_PREVIEW_URL_TEMPLATE=`) for your HTTP(S) reverse proxy, and use `devkitWorkspaceSource()` from `@docouno/env/vite` to accept the exact rendered frontend hosts. Its serve behavior covers `./dist/...` library exports, `react-client` `"development": "./src/..."` exports, zero-library projects, string `/api` proxies with WebSocket forwarding, and bounded recovery of a failed first Vite HMR handshake. Custom HMR routing remains user-controlled. Unsupported client fragments retain native behavior with a warning.

`init --preset fullstack-web` creates Rust API + React web without Electron. `make add-app name=dashboard template=react-web api=api` (`add-app --api API_SLUG`) connects a new React or Electron frontend, while managed existing API connections gain a required startup edge. Aggregate multi-app development skips Electron without `DISPLAY` unless `headless=1` is requested.

Update leaves project-owned API source, Vite configuration, `Makefile`, and `compose.yaml` in place. Review project-owned `0.4.x` files for legacy workarounds:

- In `compose.yaml`, remove manual runtime-interpolated host forwards such as `VITE_ALLOWED_HOSTS: ${VITE_ALLOWED_HOSTS:-}` (any `${...}` runtime interpolation in `compose.yaml` blocks early `stand reserve` before `make up`), and remove hardcoded `PORT: '8080'` overrides on managed APIs if adopting configurable `HOST`/`PORT` starter defaults.
- In the root `Makefile`, remove obsolete `dev-web: dev-api` ordering workarounds and raw `sh .devkit/runtime/devkit.sh cli exec ... -- npm ...` wrapper targets in favor of `make exec`.
- If your Vite config lacks the Devkit plugin, import `devkitWorkspaceSource` from `@docouno/env/vite` and add `devkitWorkspaceSource()` to its `plugins` array. See [development stands](../workflows.md#development-stands-and-preview-urls).

## Make targets and Worktrunk

The managed include adds `info`, `add-app`, `add-package`, `register`, `update`, and `recover` (`make status` remains a quiet alias for `make info`). GNU Make keeps the last recipe when two targets share a name: rename any colliding custom target in your root `Makefile` before upgrading, or invoke `sh .devkit/runtime/devkit.sh cli <subcommand> ...` directly.

New `0.5.0` projects generate project-owned `AGENTS.md` and `.config/wt.toml` on `init` (unless `--no-agents-md` or `--no-worktrunk` is passed); `devkit update` never creates or overwrites them on existing repositories. When adopting multi-worktree workflows in an upgraded `0.4.x` repository:

1. Add `/.worktrees/` to `.gitignore` if you place linked worktrees inside the repository directory.
2. Refresh any project-owned `AGENTS.md` command examples to use `make info`, `make add-app`/`make update`, and `make exec app=<name> write=1 network=bridge command='pnpm add <pkg> --lockfile-only --ignore-scripts'` (with `-w` at the workspace root).
3. To integrate [Worktrunk](../workflows.md#use-worktrunk), save `.config/wt.toml` at the repository root:

```toml
# Worktrunk runs approved project hooks in the target checkout.
# Pass --yes in non-interactive sessions or run wt config approvals add --yes.
# Enable the optional start with DEVKIT_WT_AUTOSTART=1.
[pre-start]
devkit-reserve = "sh .devkit/runtime/devkit.sh worktree-hook reserve"

[post-start]
devkit-start = "sh .devkit/runtime/devkit.sh worktree-hook start"

[pre-remove]
devkit-remove = "sh .devkit/runtime/devkit.sh worktree-hook remove"
```

In non-interactive shells and PTY-backed automation agents, pass `--yes` (`wt switch --create --no-cd --yes <branch>` and `wt remove --foreground --yes <branch>`, or approve hooks once via `wt config approvals add --yes`) so Worktrunk never blocks waiting on interactive hook-approval prompts.
