# Devkit 0.5.0 Migration

## Migrate Node workspaces to pnpm

Update on a Git branch with `devkit update . --to 0.5.0 --preview`, then apply the same command without `--preview`. The transaction creates `pnpm-workspace.yaml` and `pnpm-lock.yaml`, removes the root npm lock and `package.json` workspace list, migrates registered component links to `workspace:*` (`workspace:^` between explicitly public libraries), and removes legacy npm linking keys from `.npmrc`. It retains root dependency declarations, registry routes, token placeholders, product code, product dependency selections, and user scripts. Peer-only local links gain a workspace development dependency while retaining their peer range. When npm installed the same artifact with different transitive versions, migration preserves the variant reached by product dependencies over tooling-only variants. Conflicting product variants require `--reconcile-lock`, which permits explicit transitive resolution changes when the old graph cannot be retained. An interrupted transaction is reversible with `devkit recover .`.

Implicit `.pnpmfile.cjs`, `.pnpmfile.mjs`, and `.pnpmfile.js` hooks are unsupported. Move installation work into package lifecycle scripts, which Devkit runs in its separate offline phase.

If an npm project already contains `pnpm-lock.yaml` or `pnpm-workspace.yaml`, move those files aside before updating. Migration refuses destination collisions before staging changes. Read-only inspection of accepted `0.4.x` projects keeps their npm format and configuration policy. Existing `packageManager` and `devEngines` metadata is preserved; commands run by Devkit use its verified pnpm and container Node pins with automatic manager and SDK installation disabled.

The admitted workspace settings include `minimumReleaseAgeExclude` entries for exact `name@version` selections emitted by pnpm. Wildcards and version ranges in that list are unsupported; sync preserves admitted entries.

Review product-owned scripts and CI commands before running the gates:

- Replace `npm run --workspace=apps/web check` with `pnpm --dir apps/web run check`.
- Replace dependency mutations such as `npm install zod` with `devkit exec --component apps/web --write --network bridge -- pnpm add zod`.
- Use `workspace:^` only for runtime links between registered libraries with explicit `"private": false`; publishable packages cannot depend on private libraries or applications. `pnpm pack` rewrites the specifier to a registry SemVer range and Devkit validates the source manifest first.
- Keep npm for optional `npx` CLI entry points and publishing verified `.tgz` archives with provenance.

Run `make setup`, `make check`, `make test`, and `make build`, then review and commit all migration changes. Setup fetches the verified pnpm executable on first use; metadata commands and Rust-only projects do not. For an offline Node checkout, warm the executable and package store with setup while network access is available.

`DEVKIT_CACHE_DIR` defaults to `~/.cache/docouno/devkit` and now includes `tools/`, `pnpm-store/`, `pnpm-cache/`, `cargo/`, and `electron/`. Place it on the checkout filesystem for hardlinks. GitHub Actions can use `${{ runner.temp }}/devkit-cache`; GitLab CI can use `$CI_PROJECT_DIR/.devkit/cache/ci`. Cache keys should include `pnpm-lock.yaml`, `.devkit/manifest.json`, and Cargo locks. If the selected cache is on another mount, the package store falls back to the repository's common Git directory or the non-Git checkout's `.devkit/cache/pnpm-store`; other caches retain their configured locations.

Daily gates and development services protect `node_modules/.pnpm` from writes. Setup and explicit Node write sessions share a mount with the package store while hiding unrelated sibling directories and `.env` credentials. Local registry routes stay in `.npmrc`; networked Node commands receive a sanitized temporary user config, required environment placeholders, and an optional `DEVKIT_CA_CERT`. Offline Node and Rust tasks never receive registry credentials.

Cold pnpm acquisition supports scoped `_authToken=${TOKEN}` (Bearer) and `_auth=${BASIC_AUTH}` (base64 Basic) placeholders. Credentials follow the longest matching registry path and stay bound to the original origin during redirects.
